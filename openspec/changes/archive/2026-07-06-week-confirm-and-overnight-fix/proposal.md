## Why

The Week view carries a Notes-feature "Inbox" toggle that doesn't belong on a schedule-review screen and adds to a page that already feels busy, while lacking the one action a user actually wants there: confirming the day's schedule into real logs, like Day view already offers. Compounding this, confirm-day cannot recognize an overnight block (e.g. a nightly Sleep block) as elapsed when viewed from the day it ends — `hasBlockElapsed` unconditionally returns `false` for any overnight block regardless of the current time, so a user checking "today" in the afternoon, after last night's sleep already finished, is told there is nothing to confirm. This directly blocks the most common overnight use case (Sleep) from ever being confirmable from the day it actually completes.

## What Changes

- Remove the Inbox toggle button and `InboxPanel` from `src/pages/WeekPage.tsx`. **Correction during implementation**: Week view turned out to be the Inbox feature's *only* UI entry point in the app — removing it there made the feature unreachable, not just relocated. Confirmed with the user, who chose to delete the feature outright rather than find it a new home: `InboxPanel.tsx` and its test are deleted, along with now-unused `notes.inbox*`/`week.inbox*` i18n keys and the 3 e2e specs that exercised it from Week view. The underlying data layer (`useInboxItems`/`useAddInboxItem`/`useArchiveInboxItem` hooks, the `inbox_items` resource/table, and the AI weekly-planner's now-permanently-empty inbox-context integration) is left in place — tearing that out is a backend/data-safety decision (RLS, migrations, existing user data) out of scope here, and is flagged as a follow-up.
- Add a Confirm Day action to Week view for "today" (visible only when today falls within the displayed week), reusing the existing `ConfirmDayButton`/`buildConfirmDayRows`/`useConfirmDayMutation` logic rather than duplicating it. Scoped to today only for this change — confirming arbitrary past days from Week view is not in scope.
- **BREAKING** (behavior change, not a stored-data format change): re-scope which calendar day's confirm action recognizes an overnight schedule block as active/elapsed. Currently, an overnight block (end time earlier than start time, e.g. 23:00–07:00) is only ever matched against the day it *starts* (`days_of_week.includes(weekday(D))`), and is hard-coded to never count as elapsed on that day — so it can never be confirmed via the UI at all in the case that matters (recognizing it ended before "now"). The fix: for confirm purposes, an overnight block is matched against the day *after* its scheduled start weekday (i.e. checked against `days_of_week.includes(weekday(D - 1))` when confirming date `D`), and becomes a normal elapsed check (`end_time <= now`) once matched. The resulting log keeps the **existing** date-attribution convention already used by manual overnight quick-logging (see `e2e/time-logging.e2e.ts`: an overnight entry logged from "today" is stored dated *yesterday*, the start day) — so a confirmed log is written with `date: D - 1`, `start_time`, `end_time` unchanged. Only the *which-day-can-confirm-it* logic changes, not the stored log shape.
- Same-day (non-overnight) block matching and elapsed logic is unaffected.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `confirm-day-logging`: overnight blocks are now matched against the day *after* their scheduled start weekday for confirm/elapsed purposes (previously matched — and permanently blocked — against their own start weekday). The "An overnight block becomes a single log row" scenario changes: the block is now confirmed and dated from the day it ends being viewed, not the day it's configured to start.

## Impact

- `src/lib/confirmDay.ts` — `hasBlockElapsed` and the `active` block-matching in `buildConfirmDayRows` change to support overnight blocks matched via the previous weekday; `activeBlockCount`-equivalent UI logic in `ConfirmDayButton.tsx` needs the same matching rule so "nothing scheduled" vs "not elapsed yet" states stay accurate.
- `src/components/day/ConfirmDayButton.tsx` — no prop/API changes expected, but its `activeBlockCount` calculation (currently duplicating the same-weekday-only matching) must be updated to match the new rule, or refactored to reuse a shared matcher from `confirmDay.ts`.
- `src/pages/WeekPage.tsx` — remove `Inbox` import, `inboxOpen` state, the toggle button, and the `InboxPanel` render block; add a `ConfirmDayButton` instance (or equivalent) for today, wired to the week's already-fetched `blocks`/`logs`/`categories`.
- `openspec/specs/confirm-day-logging/spec.md` — delta spec updates the "overnight block" scenario to reflect end-day confirmability.
- Not in scope: `src/lib/gaps.ts` (`blocksOnDay`) and `src/lib/plannedMinutes.ts` already split an overnight block's minutes across both calendar days it spans (a different, already-correct per-day attribution used for rendering/charting) — no change needed there.
- i18n: remove now-unused `week.toggleInbox`/`week.inbox` and `notes.inbox`/`notes.inboxPlaceholder`/`notes.newInboxItem`/`notes.inboxEmpty`/`notes.archiveItem` keys; no new strings expected since `ConfirmDayButton` is reused as-is.
- Guest + cloud parity: reuses existing `useConfirmDayMutation` (already guest/cloud-parity per `confirm-day-logging` spec) — no new backend work. **Found and fixed a related real bug**: the `confirmDay` resource function (`src/lib/dataStore.ts`) independently re-fetches its own data on mutation and was only fetching logs for the single confirmed date, not `[date-1, date]` — this would have broken tail-instance overlap/idempotency detection in actual (non-preview) use. Widened to `[date-1, date]` in both guest and cloud branches.
- Tests: `src/lib/confirmDay.test.ts` needs new/updated cases for previous-weekday overnight matching; new `src/pages/WeekPage.test.tsx` (none existed) covers Inbox absence and the new Confirm Day button; guest E2E updated (`e2e/confirm-day-logging.e2e.ts`, new `e2e/week-view.e2e.ts`, `e2e/daily-notes.e2e.ts`'s now-removed Inbox specs, `e2e/guided-tour.e2e.ts`'s log-count assertion which now correctly includes the previously-missed overnight Sleep confirmation).
- Follow-up (not done here): remove the Inbox feature's backend/data layer entirely — `useInboxItems`/`useAddInboxItem`/`useArchiveInboxItem` in `src/lib/dataStore.ts`, `src/resources/types/inboxItem.ts`, the `inbox_items` table/migration, the `inbox_items` field in the AI weekly-plan edge function contract, and `AIPlanPanel.tsx`'s now-dead read of it — since it's now unreachable and will always be empty.
